# Runner security boundary

`services/runner/` contains fixed LaunchGate code only. It imports Node primitives and the shared contracts; it has no database/provider client, environment credential lookup, repository loader or customer-code execution. `services/orchestrator/` owns database commands, signing and artifact persistence. The runner receives a signed per-attempt capability, a public verification key and the fixed internal control endpoint.

The `RunnerProvider` interface requires idempotent launch by attempt ID, externally enforced deadline, termination, and confirmed cleanup. `isolatedRunnerSpec` constructs a fresh allowlisted environment containing only the control origin and public key; the grant travels through stdin, not command-line arguments. It requires a pinned image digest and declares the scoped egress requirement. It does not implement or prove that requirement. There is no configured production backend or default local launch fallback. A managed sandbox, microVM or appropriately isolated container backend must implement these requirements before deployment. Node worker_threads are not a sandbox. Local Docker proof would not establish production arbitrary-code isolation; Docker is used here for database tests only.

Ed25519 uses Node's crypto implementation, with algorithm fixed by key type. The signed strict-schema payload binds audience/issuer/JTI, job/attempt/fence/run, tenant/project, snapshot/commit, exact deployment/host, authorization version, operations/ceilings, invariant versions and runner identity/version. Database START consumes the JTI once. Signed grants are capabilities: disclosure grants the scoped authority until expiry/revocation, so never log them. Use TLS and private ingress for the internal service. Browser bearer tokens and unsigned payloads cannot authenticate there.

Internal routes are POST `/internal/runner/{start,check,request,evidence,fail}`. All require a valid unexpired signed capability. Service requests are bounded and safe errors omit diagnostics. Runner control requests have a two-second timeout and reject redirects. A one-second heartbeat aborts transport when current authorization/fencing is lost. The grant is not a general DB RPC capability; it cannot claim jobs, alter fences or authorize another scope.

Preview bypass secrets may be injected into the runner's trusted transport adapter only with their exact host. They are sent through `x-vercel-protection-bypass`, never query parameters, and never across redirects. Account-wide Vercel tokens, GitHub private keys, Supabase service credentials and billing credentials must never enter the runner. The provider integration host must implement secret delivery; the execution grant itself contains none.

Production prerequisites: deploy separate service identities, rotate signing keys with bounded overlap, pin runner image, enforce egress and resource limits outside the process, implement backend kill/cleanup guarantees, and operate private artifact retention. Tests verify protocol/service boundaries and synthetic cancellation, not a cloud sandbox or a compromised-kernel threat model.
